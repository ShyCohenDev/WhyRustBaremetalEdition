Why Rust? Bare-Metal Edition

Why Rust? Bare-Metal Edition

This research examines whether Rust can replace C/C++ as our language for bare-metal programming, and what we would gain and lose by making the switch.

Motivation

At our company, we generally use C/C++ for bare-metal programming and Rust for software that runs on a full operating system. There are several reasons why moving everything to Rust could benefit us:

  1. The general “Why Rust?”: memory safety, modern syntax, pattern matching, a growing community, and more.
  2. A single language: when there is one language instead of two, there is less for the average developer to learn and keep up with.
  3. No more duplicated code: logic shared between our Rust and C codebases is currently written twice, because the options for calling between Rust and C (FFI, the foreign function interface) are not good enough. These FFI options are examined later in this research.
  4. Something better than C: switching gives us a chance to move to something better than the C we currently use.

Hardware Access and Peripheral Ownership

Bare-metal in short

A bare-metal program runs directly on a microcontroller, with no operating system. It starts at power-on and never exits. The chip has a CPU, flash (the program), RAM (variables), and peripherals: hardware blocks for pins (GPIO), serial buses (UART, SPI, I2C), timers, and so on.

You control a peripheral through its registers: 32-bit locations at fixed addresses. Writing to address 0x4002_0018 does not store anything in RAM; it changes the voltage on a pin. Register accesses must be volatile, which tells the compiler to perform every read and write exactly as written, because the hardware reacts to them.

Examples use the ST Nucleo-F401RE board (STM32F401, ARM Cortex-M4). Its LED is on pin PA5.

Registers

Each register is split into bit fields. For example, GPIOA_MODER has 2 bits per pin: 00 = input, 01 = output, 10 = alternate function, 11 = analog.

Where register descriptions come from

The vendor is the company that makes the chip: ST (STM32), Nordic (nRF), NXP, Microchip, Raspberry Pi (RP2040), Espressif (ESP32) and so on. Each publishes a reference manual describing every register.

CMSIS (Common Microcontroller Software Interface Standard) is Arm’s standard for Cortex-M software. Arm writes the parts common to every Cortex-M core (e.g. core_cm4.h); each vendor writes the parts for its own chips. Two of these parts matter here:

  • Device headers (e.g. stm32f401xe.h): C structs and macros for every register. This is what C firmware uses.
  • SVD files (System View Description, e.g. STM32F401.svd): the same information as machine-readable XML: every peripheral, register, field, and the meaning of each value. Debuggers use it to show registers by name; Rust tools use it to generate code. Espressif also publishes SVD files for its RISC-V and Xtensa chips, so the format is not limited to Arm.

Both ship in the vendor’s CMSIS-Pack (Device Family Pack), downloadable from Arm’s pack index, and usually also on the vendor’s site or GitHub (e.g. inside ST’s STM32CubeF4). The Arm-written parts are open source at ARM-software/CMSIS_6.

In C

The CMSIS device header gives each register a name and each bit a macro:

RCC->AHB1ENR |= RCC_AHB1ENR_GPIOAEN;                       // turn on port A's clock
GPIOA->MODER = (GPIOA->MODER & ~GPIO_MODER_MODER5)
             | GPIO_MODER_MODER5_0;                        // PA5 = output (01)

The macros are plain integers, so the compiler accepts mistakes like these:

GPIOA->ODR = RCC_AHB1ENR_GPIOAEN;    // a mask that belongs to a different register
GPIOA->MODER |= 3u << 10;            // meant output (01), wrote analog (11)

In Rust

There are several ways to reach a register. The first two are part of the language; the rest are ordinary crates (libraries).

Raw volatile access

The address and masks are plain integers, so this looks like C and allows the same mistakes:

#![allow(unused)]
fn main() {
const GPIOA_MODER: *mut u32 = 0x4002_0000 as *mut u32;
unsafe {
    let v = GPIOA_MODER.read_volatile();
    GPIOA_MODER.write_volatile((v & !(0b11 << 10)) | (0b01 << 10));   // PA5 = output (01)
}
}

Inline assembly

Rarely written by hand: the cortex-m and riscv crates wrap the common cases (e.g. cortex_m::interrupt::disable() emits cpsid i).

PAC (Peripheral Access Crate)

A PAC is the Rust counterpart of the CMSIS device header: one crate per chip, with a definition for every peripheral, register and field. The difference is that registers, fields and values are types and methods instead of integers, so the compiler can tell them apart. Nobody writes these by hand; they are generated from the vendor’s SVD file.

With the stm32f4 PAC, the C example becomes:

#![allow(unused)]
fn main() {
dp.RCC.ahb1enr().modify(|_, w| w.gpioaen().enabled());   // turn on port A's clock
dp.GPIOA.moder().modify(|_, w| w.moder5().output());     // PA5 = output
}

modify does a volatile read-modify-write; inside it you name only the fields you change. Every field is a method that exists only on its own register, and values have names (output()) instead of bit patterns. The first C mistake is a compile error (no gpioaen field on ODR), and the second would require writing analog() explicitly. Raw bits can still be written through unsafe { w.bits(..) }. The generated code is the same load, mask and store as the C version.

How a PAC is made:

  1. Take the vendor’s SVD file.
  2. Fix its errors, which are common (e.g. stm32-rs applies YAML patches with svdtools).
  3. Run svd2rust, which turns the SVD file into Rust source.
  4. Publish the result on crates.io (stm32f4, nrf52840-pac, rp2040-pac, …). Users add it as a dependency and never run svd2rust themselves.

Chips without an SVD file need their registers written by hand with one of the other options.

Is it standard? svd2rust is the de facto standard in Rust, maintained by the Rust Embedded Working Group and used by most PACs. It is not a vendor standard like CMSIS: apart from Espressif, vendors do not ship Rust PACs; the community does.

Ownership: who may touch the hardware

In C, registers are global: any file can reconfigure any peripheral at any time. Two drivers configuring the same pin differently is found on the bench, if at all.

Rust’s ownership rules (see the Rust book, ch. 4) say every value has one owner, and passing it somewhere moves it: the old name can no longer be used. svd2rust PACs use this: each peripheral is a value you can get only once, and a driver takes it over:

#![allow(unused)]
fn main() {
let dp = pac::Peripherals::take().unwrap();   // PAC: succeeds only the first time

let uart = Uart::new(dp.USART2, ...);         // USART2 moves into the driver
let other = Other::new(dp.USART2, ...);       // compile error: value already moved
}

These values are zero bytes in size; the address is part of the type. The tracking happens in the compiler and costs nothing at runtime. It holds for code that goes through the PAC or HAL; raw volatile access can still write any register (chapter 3).

HAL crates

HAL (Hardware Abstraction Layer) is a general concept: a layer of driver functions (gpio_set, uart_write, …) over the raw registers. ST’s STM32Cube HAL is the usual one in C.

In Rust there is no single HAL. Each chip family has its own HAL crate, built on that family’s PAC:

The examples below use stm32f4xx-hal.

Typestate: a pin’s mode is part of its type

In C, the compiler doesn’t know a pin’s mode, so toggling (flipping high/low) a pin you never set as output still compiles:

__HAL_RCC_GPIOA_CLK_ENABLE();
GPIO_InitTypeDef init = { .Pin = GPIO_PIN_5, .Mode = GPIO_MODE_OUTPUT_PP };
HAL_GPIO_Init(GPIOA, &init);
HAL_GPIO_TogglePin(GPIOA, GPIO_PIN_5);   // compiles even without the Init lines

Typestate is a pattern where an object’s state is stored in its type. In stm32f4xx-hal, a pin is PA5<Input> or PA5<Output> (input: the pin reads a voltage, e.g. a button; output: the pin drives a voltage, e.g. an LED), and only output pins have toggle():

#![allow(unused)]
fn main() {
let pin = dp.GPIOA.split().pa5;              // PA5<Input>
pin.toggle();                                // compile error
let mut led = pin.into_push_pull_output();   // PA5<Output>
led.toggle();                                // OK
}

The mistake becomes a compile error, at no runtime cost. Embassy and esp-hal do the same with an Output driver: Output::new(p.PA5, ...).

Limits

  • These checks come from the libraries, not the language. Raw volatile access has none of them.
  • The PAC checks names and values, not order: forgetting a step still compiles. HAL crates catch more.
  • HAL coverage varies by chip family.
  • Typed APIs are verbose, and compiler errors for generic code take time to get used to.

Interrupts and Shared State

The problem

An interrupt lets a peripheral (e.g. a timer) pause the CPU: the CPU saves where it was, runs an interrupt handler function, then continues where it stopped. Saving the CPU registers is automatic (done by the hardware on Cortex-M); keeping shared variables consistent is not.

A handler can run between any two instructions of main. When both change the same variable, updates get lost:

uint32_t counter;
void TIM2_IRQHandler(void) { counter++; }   // interrupt handler of timer 2
int main(void) { counter++; }                // compiles to 3 instructions: load, add, store

main:    load counter   → 5
                              ── interrupt ── handler: counter = 6
main:    add 1          → 6
main:    store 6               (the handler's increment is lost)

Such a race condition can fail once a week and never on the developer’s desk.

Finding the handler

The CPU finds handlers through the vector table (a list of handler addresses at the start of flash). In C, the table comes from the vendor’s startup file, and your handler is matched by name:

void TIM2_IRQHandler(void) { ... }   // replaces the default handler
void TIM2_IRQhandler(void) { ... }   // typo: compiles, never called; the chip freezes in the default handler

In Rust, the PAC generates the vector table, and its #[interrupt] attribute checks the name against the chip’s list of interrupts:

#![allow(unused)]
fn main() {
#[interrupt]
fn TIM2() { ... }   // compile error if the chip has no TIM2 interrupt
}

Sharing a variable with a handler

In C, the fix is a critical section (interrupts turned off around the access, so nothing can run in between):

__disable_irq();
counter++;
__enable_irq();   // wrong if interrupts were already off: this turns them back on

Nothing forces it. A shared variable looks like any other global, so a missing critical section compiles.

In Rust, a global that can change is a static mut, and every access to it needs unsafe. The race can still be written, but not by accident. Safe code uses one of two tools instead:

Atomics (core::sync::atomic, part of Rust), for single numbers. The CPU does load, add and store as one step that cannot be interrupted:

#![allow(unused)]
fn main() {
static COUNTER: AtomicU32 = AtomicU32::new(0);
COUNTER.fetch_add(1, Ordering::Relaxed);   // no critical section needed
}

Not every chip has these instructions (Cortex-M0 has no fetch_add).

A critical-section mutex (the critical-section crate, used by most HAL crates), for anything bigger. The data can only be reached with a token (cs) that exists only while interrupts are off:

#![allow(unused)]
fn main() {
static STATS: Mutex<RefCell<Stats>> = Mutex::new(RefCell::new(Stats::new()));

critical_section::with(|cs| {             // interrupts off; previous state restored after
    STATS.borrow_ref_mut(cs).count += 1;  // without `cs`: compile error
});
}

A forgotten critical section becomes a compile error, at the same cost as the C version. It is verbose.

DMA

DMA (Direct Memory Access) is hardware that copies data between RAM and a peripheral without the CPU. While a transfer runs, the buffer belongs to the hardware, but in C nothing stops the code from changing or freeing it:

void send_status(void) {
    uint8_t buf[64];                          // local: lives on the stack
    HAL_UART_Transmit_DMA(&huart2, buf, 64);  // starts the transfer and returns
}   // buf is gone, but the DMA keeps reading that memory. Compiles fine.

In HAL crates, starting a transfer moves the buffer in, and finishing gives it back (simplified; the exact API differs per HAL crate):

#![allow(unused)]
fn main() {
let transfer = Transfer::start(dma_channel, uart_tx, buffer);   // buffer moves in
buffer[0] = 1;                                                  // compile error: buffer was moved
let (dma_channel, uart_tx, buffer) = transfer.wait();           // buffer moves back
}

The buffer must also live for the whole program ('static), so the stack buffer above is rejected. Embassy gets the same result with async: the buffer is borrowed until the transfer’s .await finishes.

Memory Safety, Errors and unsafe

On a PC, the operating system stops a program that accesses bad memory (“segmentation fault”). On bare-metal nothing stops it: a memory bug silently corrupts another variable, and the device fails later, somewhere unrelated.

RAM in short

Global variables sit at the start of RAM. The stack (local variables and function calls) starts at the end of RAM and grows down toward them. Most firmware has no heap (malloc), because allocation failures and fragmentation are hard to handle on a device nobody watches.

Panics

In C, writing past the end of an array is not detected. The write lands on whatever comes next in RAM, and the program keeps running with corrupted data:

uint8_t buf[4];
buf[i] = 1;   // i == 4: overwrites the next variable, no error

A panic is Rust’s reaction to a bug detected while the program runs. The same write checks the index first and, if it is out of range, stops the normal program and calls the panic handler instead:

#![allow(unused)]
fn main() {
let mut buf = [0u8; 4];
buf[i] = 1;   // i == 4: panic "index out of bounds: the len is 4 but the index is 4", with file and line
}

Every bare-metal program must choose its panic handler. A ready-made crate is usually used, or you write your own:

  • panic-halt: loops forever. The device freezes in a known place, where a debugger can inspect it.
  • panic-reset: restarts the chip, like pressing its reset button. The device recovers, but loses its current state.
  • panic-probe: prints the message, file and line on the developer’s PC through the debug probe. For development.

A custom handler is a few lines. This one restarts the chip, like panic-reset:

#![allow(unused)]
fn main() {
#[panic_handler]
fn panic(_info: &PanicInfo) -> ! {    // `!`: never returns
    cortex_m::peripheral::SCB::sys_reset();   // restart the chip
}
}

Production code usually avoids panics, e.g. buf.get(i) instead of buf[i]: buf[i] panics when out of range, while buf.get(i) returns an Option (the value, or None) that the caller must check.

What Rust does not catch

  • Stack overflow: same as C. A tool (flip-link) places the stack so an overflow causes an immediate fault instead of corruption.
  • Logic bugs: wrong formulas, wrong protocols, wrong timing.

unsafe

Some operations cannot be checked by the compiler, because their correctness depends on the hardware or on other code. Rust allows them only inside an unsafe block (unsafe { ... }), where the programmer, not the compiler, promises they are correct. On bare-metal these are mainly:

  • Reading or writing through a raw address (a raw pointer), e.g. a hardware register.
  • Calling a function marked unsafe, which includes every C function.
  • Accessing a changeable global (static mut), e.g. one shared with an interrupt.

unsafe does not turn the other checks off: types, ownership and bounds checks still apply inside the block.

The standard pattern: a small unsafe core inside a safe function.

#![allow(unused)]
fn main() {
impl Pa5<Output> {
    pub fn set_high(&mut self) {
        // SAFETY: 0x4002_0018 is GPIOA's BSRR register. Writing bit 5 sets only PA5,
        // and we own the only Pa5 value.
        unsafe { (0x4002_0018 as *mut u32).write_volatile(1 << 5) };
    }
}
}

Application code calls led.set_high(), which is safe. In a typical firmware, unsafe lives in libraries (the PAC, the HAL, the startup code), and application modules can forbid it entirely with #![forbid(unsafe_code)].

Why it matters: undefined behavior can come from any line of C, but only from unsafe blocks in Rust. When memory is corrupted, the search is limited to those blocks, and reviews can focus there. The honest limit: a bug inside unsafe code, including in a library, can still corrupt memory.

Should We Switch?

This chapter weighs the reasons for and against moving our bare-metal code from C to Rust, based on the three technical chapters.

Reasons for

  1. Whole classes of bugs become compile errors. Hardware conflicts, unprotected data shared with interrupts, DMA buffer misuse, out-of-bounds access, ignored errors. In C these are found on the bench or in the field. (Ch. 1, 2, 3)
  2. One language for the whole company. We already use Rust on the OS side. Developers would know one language, not two.
  3. No more code written twice. Shared logic becomes one no_std library used by both bare-metal and OS code.
  4. Better daily tooling. One command to build, flash and see logs; built-in unit tests; reproducible builds.
  5. Same runtime cost. No runtime and no garbage collector; most safety checks happen at compile time.

Reasons against

  1. Learning curve. Ownership, borrowing and generics take C developers time to learn. Bare-metal Rust adds its own patterns (typestate, critical-section tokens).
  2. Chip support varies. Excellent for some chip families, partial for others. Missing drivers must be written by us.
  3. Libraries are mostly community-maintained, not vendor-maintained, and many are below version 1.0.
  4. Fewer certified components. Qualified compilers exist (Ferrocene), but certified RTOSes and middleware are mostly C.
  5. Migration cost. Existing C code is tested and working. Rewriting it costs time and carries the risk of new bugs.
  6. Some things are more verbose. For example sharing data with interrupt handlers, and long type names in HAL code.

Recommendation

Move to Rust for new bare-metal code: it turns whole classes of firmware bugs into compile errors at the same runtime cost, and lets the company work in one language.
